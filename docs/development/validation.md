# Validation

## Reproducible baseline — 2026-10-02 continuation

The current evidence is generated by **checked-in** `tests/regression.c` and
`tools/check-wasm.mjs`, not an unshipped exploratory harness. Assertions remain
active in Release builds; `NDEBUG` cannot turn the suite into a no-op.

| Local check | Observed result | Scope |
| --- | --- | --- |
| GCC 14.2 Release build and CTest | Pass | Native C17 core and CLI |
| Clang 17 Debug ASan/UBSan and CTest | Pass | Same core regression with sanitizers |
| Native / WASM shared regression | 83,297 assertions each, zero failures | Reference-derived cases; not exhaustive CPU conformance |
| Six-profile synthetic guest | All six pass | Production native CLI vs production WASM; state, UART, pixels and reset/replay |
| JavaScript syntax and WASM build | Pass | Not browser lifecycle E2E |
| Documentation navigation/local targets | Pass | Not itself a Zensical render |

The suite was first run against the published import source (`2840885`). It
reported nine failing assertions, covering the rejected legal Thumb BX PC,
incorrect operand acceptance and missing watchdog MMIO. The corrected core
passes. The baseline stops its watchdog test at the first unsupported access,
so its assertion count is lower; this is not nine distinct root causes.

Seed: `0x09202410`. The suite uses independent 64-bit/signed arithmetic and an
iterative shifter oracle, then exercises actual ARM/Thumb decode, register
banks, exception return, selected MMU permissions, physical bounds, UART,
watchdog dividers/reload/IRQ and six model initialization/reset paths.
Native/WASM comparison detects portability divergence; it is **not** a
comparison against an independent ARM emulator.

## Commands

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
./build/orchard-regression
npm run check
npm run build
npm run test:wasm

cmake -S . -B build-sanitize -DCMAKE_C_COMPILER=clang \
  -DCMAKE_BUILD_TYPE=Debug -DORCHARD_SANITIZE=ON
cmake --build build-sanitize --parallel
ctest --test-dir build-sanitize --output-on-failure
python3 tools/check-docs.py
```

`npm run test:wasm` expects the native Release binaries under `build/`.
`ORCHARD_BUILD_DIR` selects another build directory. It compiles a test-only
WASM module under that directory, compares assertion counts/results, and
loads the independently built production `dist/orchard.wasm` for integration.
No test module enters `dist/` or the CMake install targets.

The integration script constructs its own full-size synthetic NOR files in a
unique temporary directory. It disables the watchdog through guest MMIO,
executes ARM/Thumb and a legal BX PC transition, takes/returns from SWI,
emits and echoes UART bytes, programs a nonblank provisional LCD buffer and
enters WFI. It compares CLI JSON, UART bytes and PGM pixels against WASM,
then repeats the WASM execution after cold reset. Temporary files are removed
on success or failure. **These generated inputs are not HP firmware.**

## Hardware behavior added in this slice

References: [Samsung S3C2410A manual](references.md), pages 3-18, 3-23,
3-26, 4-15 and 18-1 through 18-4.

Thumb BX PC is implemented at word alignment; the non-word-aligned case
remains an explicit unpredictable-operation stop. ARMv4 multiply destination /
Rm restrictions and MSR's R15 restriction are checked before mutation.

Watchdog WTCON/WTDAT/WTCNT now expose their reset values, 16-bit counters,
prescaler and four dividers. WTDAT does not initialize WTCNT on a write;
expiration reloads the counter and can pend interrupt 9. Disabling the counter
stops countdown. Unsupported width/address accesses still stop.

One scheduler tick is one **provisional functional PCLK quantum**, not real
elapsed time. Live divider phase and PLL clock ratios are not hardware-verified.
A requested watchdog reset stops with `ORCHARD_UNIMPLEMENTED_RESET`; it does
not erase SRAM and pretend the physical reset domain has been implemented.
The scheduler counts the tick that produces such a peripheral stop.

## Remaining gates and remote results

A strict Zensical render could not run locally because the package is absent
and network/DNS access failed. The workflow runs the strict build on the
configured runner; observed remote conclusions belong in
[issue #1](https://github.com/zyf722/orchard-emu/issues/1) and the associated
Actions run, not in an assumed local pass. Static-analysis results are checked
by the workflow and may be reproduced with `clang --analyze`.

No real HP NOR was executed, no browser lifecycle test was rerun, and no stock
keyboard/UI, native stock payload return, SD or USB transfer is accepted.
Cache/TLB details, undefined exceptions, multiple-access abort/writeback and
complete peripheral semantics remain open. The historical 74,970 assertions
and 200,000 dispatches from the first downloadable handoff are **not** the
current reproducible acceptance counts; retain that report only as history.
